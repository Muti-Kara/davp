# Mini GenomicKB graph

This directory holds the small, **synthetic** knowledge graph that the demo's
`inGeneTopMatch` algorithm traverses. It stands in for **GenomicKB** — the biomedical
knowledge graph DAVP uses in production (~3.5 × 10⁸ typed nodes, ~1.4 × 10⁹ edges, served
from Neo4j), which cannot be redistributed.

The schema mirrors the GenomicKB node/relationship types that `inGeneTopMatch` actually
queries, so the ported algorithm runs against it unchanged in spirit (only the storage
backend differs: a JSON file + a CSV instead of Neo4j + a sorted GWAS/ClinVar index).

## Files

| File | Mirrors (production) | Contents |
|------|----------------------|----------|
| `graph.json` | GenomicKB nodes + relationships (Neo4j) | `chr_chain` tiles, genomic entities, `phenotype_or_disease` ontology nodes, GWAS-association variant nodes |
| `clinvar.csv` | the sorted ClinVar interval table kept alongside the graph | ClinVar records for interval-overlap search |

## `graph.json` schema

```jsonc
{
  "meta": { "resolution": 200, "n_variants_covered": 97, "description": "..." },

  // 200 bp segments tiling the genome (+ coarser "region" tiles), the GenomicKB chr_chain type.
  "chr_chains": [
    { "id": 1001, "chr": "15", "start_loc": 42360000, "end_loc": 42360199,
      "resolution": 200, "GC_percentage": 0.41, "neighbor_ids": [1740] }
  ],

  // Genes, transcripts, regulatory + epigenetic elements overlapping the genome.
  // `type` is the label used in the Detailed Variant Report (Gene, Transcript,
  // TF Binding Site, Histone Modification Site, ChromHMM State, ...).
  // `props.chr_chain_ids` links the entity to the tile(s) it spans.
  "entities": [
    { "id": 1812, "type": "Gene", "chr": "15", "start_loc": 42330096,
      "end_loc": 42390096, "name": "CAPN3", "props": { "chr_chain_ids": [1001] } }
  ],

  // phenotype_or_disease ontology nodes (EFO / HP / GO / MONDO ... terms).
  "phenotypes": [
    { "id": "EFO_0004509", "label": "hemoglobin measurement",
      "definition": "...", "type": "EFO" }
  ],

  // Variant nodes that carry a GWAS_association edge to a phenotype_or_disease node.
  // `rel_id` is the association id; interval-overlap search uses (chr, start_loc).
  "gwas_variants": [
    { "id": 1745, "chr": "15", "start_loc": 42360099, "rel_id": 1745,
      "phenotype_id": "EFO_0004509", "risk_allele": "A", "mlog_pvalue": 7.0,
      "accession": "GCST0001745" }
  ]
}
```

## `clinvar.csv` columns

`Chromosome, Start, Stop, ClinicalSignificance, PhenotypeList, PhenotypeIDS` — the same
essential columns the production ClinVar loader uses. Rows are sorted by
`(chromosome, Start)` so the interval lookup can bisect.

## How it was built and what is real

`graph.json` and `clinvar.csv` are generated by
[`../build_mini_graph.py`](../build_mini_graph.py), seeded from the shipped
`variant_reports/*.txt` (which were produced in production against the real GenomicKB). So,
for each demo variant:

- the **gene symbols, GWAS traits, and ClinVar phenotype names are the real ones** that
  production attached to that variant;
- entity spans are placed so wider entities (genes, transcripts) accrue more associations
  than narrow ones (TF sites, ChromHMM states), reproducing production's
  "wider entity → more evidence" behaviour; and
- node **ids are graph-local** (not the production Neo4j ids), and the **evidence volume is
  miniature** — a handful of ClinVar/GWAS records per entity instead of the tens of
  thousands GenomicKB holds.

Regenerate with:

```bash
python -m ingenetopmatch.build_mini_graph
```
